Found live, fixed (each with a test)
  1. Classic Monks: the rollback reason could lose the fatal. WordPress runs the shutdown action
     before it prints the scrape, and a notice raised there (WooCommerce, Elementor) replaces
     error_get_last(). get-http-status came back with fatal null, so the reason was only "The
     home page answered 500". Classic Monks now prints the fatal first in a checked scrape
     request (17caeeec / d456976). When no scrape has it, the reason takes it from the error
     log (8f4d1985 / a050143).
  2. Classic Monks: after a rollback, the site's update list was empty (WooCommerce's update
     vanished from Updates) until WordPress checked again. The rollback now reads it again
     (229aaa0c / 1b486bd).
  3. Monks Central: the 5-minute uptime check reached mc-a during the safe update's
     maintenance mode and showed "1 down". Monitors skip a site while a change runs on it
     (abbb706).
  Also seen: the first try ran unchecked, because the core still had mc-a's tool list from
  before Classic Monks was synced. A health check reads it again ("Check all sites now", at
  start and every 15 minutes); after that the update took the safe path. Decided in
  docs/pipeline/phase-6.md.
